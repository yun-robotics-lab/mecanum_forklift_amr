# M11c - pick and carry: Nav2 staging + DockPallet + loaded drive (simulation) - 2026-11-24

Chain per trial (`scripts/pick_trials.py`): navigate (unloaded footprint) to one of 5 start poses -> pallet_1 (+ box + marker) moved by an offset
-> `DockPallet` with `navigate_to_staging: true`, `undock_after: true` (workflow: SET_MARKER, STAGING via Nav2, fresh marker pose, opennav approach,
holonomic alignment, lift, back-out) -> Nav2 drive with the pallet on the forks to the carry goal (1.0, -1.2). MPPI controller, stop distance 0.245 m.
Start poses: (0,-1,0), (1.2,1,0), (-1.8,0,180), (-1.8,-1.6,0), (0,1,180); pallet offsets: lateral 0/+-5 cm x yaw 0/+-10 deg (7 combinations, 20 trials).
Raw data: `docs/testing/data/2026-11-24_m11c_pick_trials_raw.txt`.

## What was added for 11c
- **Staging by the workflow**: the workflow navigates to the staging pose itself (NavigateToPose, dock database pose + `staging_x_offset`) and only then waits for a fresh marker pose and calls opennav with staging disabled. (A first version waited for the marker before staging; it is not visible from the start pose.) New state `STAGING`, error code `STAGING_FAILED`.
- **Loaded footprint**: after the lift the workflow publishes the loaded polygon (front 0.435 m instead of 0.368 m) to `local_costmap/footprint` and `global_costmap/footprint` (verified: both costmaps subscribe to it); the bare-fork polygon is restored when the next dock starts.
- **Map without the picked pallet**: pallets are below the lidar plane and exist only as painted cells of the curated map. With the pallet on the forks the loaded footprint started inside "its own" obstacle and every plan aborted. After the lift the workflow loads `simple_warehouse_nav_pallet_1_picked.yaml` (generated by `make_nav_map.py ... pallet_1,box_1`, which reproduces the committed full map byte for byte) through `nav_map_server/load_map` and restores the full map at the next dock. Error code `MAP_UPDATE_FAILED`.
- Dependencies: `nav2_msgs` and `mecanum_forklift_navigation` as exec dependencies of the docking package (both already installed).

## Problems found on the way (all fixed or worked around)
- **Vision node stalls**: the node's image subscription sometimes stopped receiving silently (minutes into a run, also right after starting together with other nodes) while the camera kept publishing to every fresh subscriber; re-creating the subscription did not help. Root cause **not found**. Workaround: the node re-subscribes once after 5 s without an image, exits after 10 s, and the launch file respawns it (`respawn=True`); the workflow re-sends `target_marker_id` while waiting for a pose (a respawned node starts with -1). The 20-trial run had 0 respawns after the last reboot; the earlier interrupted run had 1-4 and still passed trials 1-4.
- The vision debug image is now off by default (CPU, ~15 MB/s); the marker perception timeout is 20 s wall (the sim runs at RTF 0.3-0.5).
- The machine powered off / rebooted twice during the work (log ends without shutdown messages; not an out-of-memory kill), so the 20 trials were run in batches and saved after each batch. `scripts/dev_stack.sh start|stop` starts and stops the whole stack.
- A stale `cmd_vel_gate` from an earlier session briefly doubled the velocity gate; it was found through the duplicate-node check.

## Not verified / open
- Pick only: no drop-off (M12); only pallet_1 (the map swap is configured per dock entry); offsets limited to +-5 cm / +-10 deg; 5 fixed start poses.
- The loaded footprint was not compared against an unswitched run (no "why the switch is needed" demonstration).
- Vision stall root cause; Nav2 has no bounded give-up time (the mission manager must time out).
- Sim masses 0.3 kg pallet + 0.2 kg box; no hardware. Simulation does not establish physical safety.
