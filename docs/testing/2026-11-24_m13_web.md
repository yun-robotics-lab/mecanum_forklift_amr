# M13 - web integration (simulation) - 2026-11-24

Package `mecanum_forklift_web_bridge`: validated REST API (FastAPI/uvicorn, port 8000), independent software e-stop node, rosbridge (9090) and `web_video_server` (8080)
launch, minimal static dashboard. Everything binds to 127.0.0.1 by default (`address` launch argument). Raw output: `docs/testing/data/2026-11-24_m13_web_tests_raw.txt`.
Tools: `scripts/web_tests.py` (9 integration cases), `dev_stack.sh start_web | stop_web`.

## Design decisions made here (ADR-0013)
- **Auth (Q-W1)**: bearer token for every endpoint except `/health` and the dashboard page; token kept in `~/.config/mecanum_forklift/web_token` (created with mode 0600),
  compared in constant time; CORS limited to a configured origin list (default none); POST /missions and cancel are rate limited (burst 5, 10/min); `/estop` never is.
- **No direct motion**: no endpoint accepts a velocity, lift height or teleop command (checked from the OpenAPI paths and by rejecting unknown body fields); missions go to
  `ExecuteMission`, nothing else reaches the robot.
- **Software e-stop**: separate `estop_node` (latched). While engaged it publishes zero Twists at 20 Hz on `cmd_vel_estop` (new top-priority `twist_mux` input, 200 > teleop 100)
  and cancels all goals of `execute_mission`, `dock_pallet`, `navigate_to_pose`, `set_lift_height` every second. Engage over REST (`POST /estop`); **release only locally**
  (`ros2 service call /estop/release std_srvs/srv/Trigger`); `POST /estop/release` is answered 403 LOCAL_ONLY. Missions are refused (423) while engaged or if the state is unknown.
  If the e-stop node is unreachable the API falls back to holding zero velocity for 5 s (goals not cancelled) and says so. Simulation-level only; a robot needs a hardware e-stop.
- **rosbridge 2.0.4 limits**: no authentication; one `topics_glob` list governs subscribe, advertise and publish together (so a client could also publish to an allowed telemetry topic);
  an empty glob string means *unrestricted*, `"[]"` means *nothing*. Launch: topics `/mission_status`, `/lift_state`, `/estop/state`; services and actions `"[]"`; `rosapi` is not started.
  Localhost only; for remote dashboards use the REST event stream.
- Video: MJPEG from `web_video_server`, localhost, `quality=50`; optional (`enable_video:=false`).

## Automated checks
- 64 unit/API tests: validators (valid, invalid, boundary), token file/compare/rate limiter, and the FastAPI app against a fake backend (all of 400, 401, 404, 409, 413, 423, 429, 503;
  no side effect on invalid requests; estop never rate-limited; release refused; no motion endpoints; internal errors hidden). Lint included.

## Not verified / open
- Remote (non-localhost) use, TLS, token rotation, multi-user roles; two instances on different ports (ports are launch arguments, not exercised); roslibjs dashboards; browser rendering of the dashboard (only fetched and API-driven in tests).
- Battery and diagnostics do not exist in this stack (reported as `null`). Status pose comes from the map -> base_link TF.
- A rosbridge client could still *publish* to the allowed telemetry topics (spoofing for other dashboard users); no robot consumer reads them.
- REST mission records are kept in memory only (last 100); a restart of the API forgets them (the mission manager's own state is separate).
- Machine power losses earlier in the project: tests were run in groups and saved after each. Simulation does not establish physical safety.
